# فاز ۳ — قابلیت‌های حرفه‌ای: DMN، تقویم کاری، Worker پایدار و SSE

این سند پیاده‌سازی فاز ۳ سند جامع نیازمندی‌ها را تشریح می‌کند: جدول تصمیم (DMN سبک)،
تقویم کاری، Worker پایدار (Celery) و رویدادهای زنده سرور (SSE).

---

## ۱) جدول تصمیم — DMN سبک (Decision Table)

**هدف:** شرط‌گذاری مسیرها بدون کدنویسی؛ جایگزین «فقط عبارت پایتونی روی متغیرها».

### مدل داده
- `decision_definitions`: کلید یکتا، عنوان، توضیح.
- `decision_versions`: نسخه‌های تغییرناپذیر با `schema_json` (ورودی‌ها، خروجی‌ها، قواعد، سیاست برخورد).
- نسخه منتشرشده تغییرناپذیر است؛ ویرایش همیشه «نسخه جدید» می‌سازد (هم‌راستا با AC-14 فرایندها).

### ساختار جدول
```json
{
  "hitPolicy": "FIRST | UNIQUE | ANY | PRIORITY | COLLECT",
  "inputs":  [{"name": "total_amount", "label": "مبلغ", "type": "number"}],
  "outputs": [{"name": "approval_level", "label": "سطح تأیید", "defaultValue": "manager"}],
  "rules": [
    {"id": "r1", "inputEntries": {"total_amount": "> 10000000", "priority": "high"},
     "outputEntries": {"approval_level": "director"}, "priority": 1, "enabled": true}
  ]
}
```

### قالب عبارت ورودی (ارزیاب امن — بدون eval/exec)
| عبارت | معنا |
|-------|------|
| خالی یا `-` | هر مقدار (Wildcard) |
| `> 100` ، `<= 50` | مقایسه عددی |
| `== 'x'` ، `!= 3` | تساوی/نابرابری |
| `between 10..20` | بازه بسته عددی |
| `in a,b,c` | عضویت در مجموعه |
| `true` / `false` | مقایسه منطقی |
| ترکیب با `&&` / `\|\|` | منطق ترکیبی بین شرط‌های یک سلول |

### سیاست‌های برخورد
- **FIRST**: نخستین قاعده منطبق (ترتیب فهرست)
- **UNIQUE**: فقط یک قاعده باید منطبق شود؛ بیش از یکی = خطای کنترل‌شده
- **ANY**: خروجی قواعد منطبق باید یکسان باشد
- **PRIORITY**: کمترین شماره اولویت برنده است
- **COLLECT**: همه خروجی‌ها به‌صورت فهرست (`{"results": [...], "matched": n}`)

### اتصال به فرایند — دو مسیر
1. **اتصال به وظیفه انسانی** (`config_json.bindings[task].decisionKey`):
   هنگام تکمیل وظیفه، جدول با داده لحظه‌ای ارزیابی و خروجی‌ها به متغیرهای فرایند ادغام
   می‌شود؛ شرط دروازه انحصاری می‌تواند مستقیماً به خروجی جدول ارجاع دهد
   (مثلاً `approval_level == 'director'`). رویداد `decision_applied` در تاریخچه ثبت می‌شود.
2. **کانکتور `dmn:<key>`** روی فعالیت سیستمی (ServiceTask):
   ارزیابی در جریان اجرا با متغیرهای فرایند؛ خطای ارزیابی → Incident قابل رسیدگی (AC-15).

### اعتبارسنجی انتشار
انتشار نسخه فرایند در صورتی که `decisionKey` به جدول موجود/منتشرشده ارجاع ندهد، مسدود می‌شود (AC-02).

### API
```
GET    /api/v1/decisions                    فهرست
POST   /api/v1/decisions                    ایجاد تعریف
GET    /api/v1/decisions/{id}               جزئیات + نسخه‌ها
POST   /api/v1/decisions/{id}/versions      نسخه جدید (با اعتبارسنجی ساختاری)
PUT    /api/v1/decisions/versions/{vid}     ویرایش پیش‌نویس
POST   /api/v1/decisions/versions/{vid}/publish     انتشار
POST   /api/v1/decisions/versions/{vid}/archive     بایگانی نسخه منتشرشده
POST   /api/v1/decisions/{id}/evaluate      آزمون ارزیابی (توسعه/تست)
```

### رابط کاربری
صفحه «جدول‌های تصمیم»: گرید قابل ویرایش قواعد، مدیریت ورودی/خروجی/سیاست برخورد،
انتشار، نسخه‌گذاری و پنل آزمون ارزیابی. اتصال جدول به فعالیت از پنل تنظیمات طراح فرایند.

## ۲) تقویم کاری (Working Calendar)

**هدف:** محاسبه مهلت وظایف بر پایه ساعات اداری واقعی به‌جای ساعت تقویمی.

### مدل داده
- `work_calendars`: نام، منطقه زمانی (پیش‌فرض `Asia/Tehran`)، برنامه هفتگی JSON، پرچم پیش‌فرض.
- `calendar_holidays`: تعطیلی یک‌باره (تاریخ میلادی ذخیره، انتخاب جلالی در UI) یا تکرارشونده سالانه.

### قواعد محاسبه
- برنامه هفتگی به تفکیک روز (شنبه تا جمعه — ترتیب هفته ایرانی): فعال/غیرفعال، ساعات، وقفه‌ها (ناهار).
- روزهای غیرفعال، جمعه، تعطیلات و وقفه‌ها از شمارش حذف می‌شوند.
- شروع خارج از ساعات کاری → از نخستین لحظه کاری بعدی.
- تقویم بدون روز کاری فعال → بازگشت به محاسبه خطی (fallback امن).
- پایگاه به‌صورت naive-UTC ذخیره می‌کند؛ تبدیل با `zoneinfo` انجام می‌شود.

### اتصال به فرایند
- `config_json.calendarId` روی نسخه فرایند (انتخاب از طراح فرایند).
- مهلت وظایف (`dueHours`) با `add_business_hours()` محاسبه می‌شود؛ در نبود تقویم، خطی.
- تقویم حذف‌شده → هشدار در اعتبارسنجی انتشار.

### API
```
GET/POST/PUT/DELETE  /api/v1/calendars[/{id}]
POST  /api/v1/calendars/{id}/holidays           ثبت تعطیلی
DELETE /api/v1/calendars/{id}/holidays/{hid}    حذف تعطیلی
POST  /api/v1/calendars/{id}/preview            پیش‌نمایش: از اکنون + ساعت کاری → مهلت
GET   /api/v1/calendars/default/summary         خلاصه تقویم پیش‌فرض
```

### رابط کاربری
صفحه «تقویم کاری»: ویرایش برنامه هفتگی (فعال‌سازی روز، ساعات، وقفه‌ها)، مدیریت تعطیلات
با انتخابگر تاریخ جلالی (یک‌باره/سالانه) و ابزار پیش‌نمایش مهلت.

## ۳) Worker پایدار (Celery)

**هدف:** انتقال زمان‌بند «سبک» فازهای قبل به Worker پایدار و پایش خودکار SLA (سند §۲۱).

### دو حالت اجرا (`BPMS_SCHEDULER_MODE`)
| حالت | کاربرد | توضیح |
|------|--------|-------|
| `inprocess` (پیش‌فرض) | توسعه و پایلوت | نخ پس‌زمینه در uvicorn؛ بدون وابستگی Redis |
| `celery` | عملیات | Worker + Beat مستقل؛ بدون تیک در uvicorn |

### وظایف زمان‌بندی‌شده (beat)
- `bpms.engine.tick` — هر ۳۰ ثانیه: بیدار کردن تایمرهای BPMN منتظر (تداوم رفتار tick فاز قبل، اکنون پایدار).
- `bpms.tasks.sla_check` — هر ۵ دقیقه: اسکن وظایف باز برای هشدار/فرازدگی.

### پایش SLA
- **هشدار**: عبور از `BPMS_SLA_WARN_PCT` (پیش‌فرض ۸۰٪) از کل زمان مجاز وظیفه → اعلان به مسئول/گروه.
- **فرازدگی**: گذشتن `due_at` → اعلان فرازدگی.
- هر حالت فقط یک‌بار به‌ازای هر وظیفه (`sla_warned_at` / `sla_escalated_at` در `engine_tasks`).
- رویداد `sla` به گذرگاه زنده منتشر می‌شود (کارتابل و داشبورد خودبه‌خود تازه می‌شوند).

### اجرا در عملیات
```bash
export BPMS_SCHEDULER_MODE=celery
celery -A app.worker.celery_app worker --loglevel=info -Q bpms -B
```

## ۴) رویدادهای زنده — SSE (Server-Sent Events)

**هدف:** اعلان و به‌روزرسانی هم‌زمان بدون نظرسنجی (سند §۲۸).

### معماری
- `GET /api/v1/events/stream?token=...` — جریان SSE با احراز هویت توکن در پارامتر
  (EventSource امکان هدر ندارد). رویدادها **به تفکیک کاربر** فیلتر می‌شوند.
- گذرگاه رویداد درون‌فرایندی: هر اتصال یک `asyncio.Queue` اختصاصی.
- انتشار از کد همگام (threadpool) با `call_soon_threadsafe` — بدون بن‌بست.
- **انتشار پس از commit**: رویدادها روی نشست SQLAlchemy صف می‌شوند و فقط پس از
  `commit` موفق منتشر می‌شوند؛ با rollback دور ریخته می‌شوند (بدون اعلان کاذب).
- **پل Redis اختیاری** (`BPMS_REDIS_URL`): در استقرار چندفرایندی، رویدادها بین
  فرایندها از طریق کانال `bpms:events` هم‌رسانی می‌شوند. نبود Redis فقط مسیر
  درون‌فرایندی را فعال می‌گذارد.
- keepalive هر ۲۵ ثانیه + پاک‌سازی خودکار اتصال‌های قطع‌شده.

### انواع رویداد
| رویداد | معنا | واکنش رابط کاربری |
|--------|------|-------------------|
| `hello` | افتتاح جریان (تعداد خوانده‌نشده) | نمایش برچسب «زنده» |
| `notification` | اعلان درون‌سامانه جدید | toast + افزایش شمارنده + به‌روزرسانی فهرست |
| `instance` | تغییر وضعیت نمونه (تکمیل وظیفه/لغو) | تازه‌سازی کارتابل/جزئیات نمونه |
| `sla` | هشدار/فرازدگی مهلت | تازه‌سازی کارتابل |

### رفتار رابط کاربری
- قلاب `useLiveEvents` با اتصال مجدد فزاینده (تا ۳۰ ثانیه) و پاک‌سازی در خروج.
- برچسب «زنده» در نوار بالا؛ toast اعلان‌ها؛ تازه‌سازی خودکار کارتابل و جزئیات نمونه.
- در نبود پشتیبانی مرورگر، به نظرسنجی دوره‌ای قبلی بازمی‌گردد (پس‌روند امن).
